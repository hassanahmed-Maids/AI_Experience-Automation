**Replace with:**
```js
  const entry = rates.applicable[0];
  out.actual_rate = entry.amount;
  out.rate_entry = entry.raw;
  // An introductory rate below card IS flagged for the months it applies. That
  // is a policy call recorded on 2026-08-19: report what was true that month and
  // let a human clear an approved promotion through needs_human, exactly as the
  // living-switch class is cleared. The flag exists so the human sees WHY.
  //
  // needs_human is set HERE, not merely flagged. Ruled 2026-08-26: the 08-19
  // policy assumes a human clears an approved promotion, and the flag alone
  // never summoned one - the case shipped as a red with the reason attached and
  // nobody asked to look at it.
  if (entry.duration_months !== null) {
    out.flags.push('bounded_rate_period');
    out.needs_human = true;
  }

  // --- CROSS-CHECK: this resolver against ERP's own numeric figure ---------
  // Ruled 2026-08-26. paymentsInfo REMAINS the rate basis - it is the only
  // month-scoped source, and currentPayment.amountValue was removed on
  // 2026-08-18 for being whatever period happens to be current
  // (rate-field-is-wrong.md). nextMonthlyPaymentAmount is a different field and
  // is used only to confirm that this parser and this supersession model agree
  // with ERP about the SAME month.
  //
  // Measured on 60 live contracts (execution 94326): the two agree 38 of 38,
  // including all ten carrying a bounded line. A disagreement is therefore not
  // a modelling difference - it means this contract's terms cannot be read
  // reliably. It is the shape the 145 wrong reds took: a resolved 693 against
  // an active rate of 4,715.
  //
  // Compared AT nextMonthlyPaymentDate, never at the audited month. A contract
  // legitimately inside a bounded window pays the promo rate in M while
  // nextMonthlyPaymentAmount already describes the standing rate, so comparing
  // across that boundary would manufacture a disagreement on every honest
  // promotion - which is precisely the signal the 08-19 policy protects.
  const npAmount = num(c.next_monthly_payment_amount);
  const npMs = parseIso(c.next_monthly_payment_date);
  if (npAmount !== null && npMs !== null) {
    const npDate = new Date(npMs);
    const npMonth = npDate.getUTCFullYear() + '-' + String(npDate.getUTCMonth() + 1).padStart(2, '0');
    const npBounds = monthBounds(npMonth);
    const npRates = npBounds ? resolveMonthlyRate(c.payments_info, npBounds.first, startMs) : null;
    if (npRates && npRates.applicable.length === 1) {
      const npEntry = npRates.applicable[0];
      if (Math.abs(npEntry.amount - npAmount) > 0.5) {
        out.state = 'pending';
        out.verdict = "Can't tell";
        out.reason_code = 'rate_conflicts_next_payment';
        out.needs_human = true;
        out.flags.push('rate_conflicts_next_payment(' + npEntry.amount + '_vs_' + npAmount + '@' + npMonth + ')');
        return out; // never price a contract whose two rate statements disagree
      }
    } else {
      // Not a failure. The next payment date can fall before every entry's
      // coverage, or inside an overlap the caller already routes on. Recorded so
      // "the cross-check passed" and "it could not run" never read the same.
      out.flags.push('rate_crosscheck_unavailable');
    }
  } else {
    out.flags.push('rate_crosscheck_no_erp_figure');
  }
```

## Notes

**No schema change.** `Write Cases` uses `autoMapInputData`, and the row is built
from an explicit field list. The new information rides on `reason_code` and on
`flags`, which the wrapper already folds into `reason_text`. Nothing new needs a
column.

**Where it sits in the gate order.** After the rate is resolved (so
`actual_rate` and `rate_entry` are still recorded for the reviewer) and before
cohort and card resolution — matching the three pendings above it
(`no_payment_plan`, `rate_unreadable`, `multiple_rates_in_month`), which also
return early.

**Declared gap.** 22 of 60 sampled contracts carry no `nextMonthlyPaymentAmount`
— mostly ending contracts. Those get `rate_crosscheck_no_erp_figure` and keep
current behaviour. The flag is recorded but does not set `needs_human`: on this
sample it would move ~37% of rows into review for no signal.

**Direction of the gate.** A disagreement pulls the row to `pending`
unconditionally, including rows that would otherwise be green. That is the
conservative direction and matches `needs_human` being one-way elsewhere in this
scorer.
