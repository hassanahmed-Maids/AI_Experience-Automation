- 2026-08-30 — **Jira deployment tickets must be written in Markdown, not Server wiki markup; verify by reading back as ADF.** `VPMGOV-1633` (Travel Assist) was submitted with `h2.` headings and `||…||` tables. Jira Cloud stores descriptions as ADF and does not interpret wiki markup, so the whole body is stored as one unparsed plain-text blob and renders literally — the reader sees `h2.` as body text and the endpoint tables as pipe soup. Diagnosis is mechanical: `getJiraIssue(responseContentFormat:"adf")` returns a plain STRING for a broken ticket and a `{"type":"doc"}` object for a good one; the escaped `\~0.03` in the stored text is a second tell. Rule: submit with `contentFormat:"markdown"`, then read back as ADF and confirm a `doc` object before calling the ticket done. Template + corrected body in `audit-flows/jira/`. TWO ACCESS LIMITS found while fixing it, both needing Jira admin: `description` is NOT on the edit screen for issue type `n8n Flow` in VPMGOV (so the API cannot reformat 1633 — it needs a UI paste), and this account **cannot create issues in VPMGOV at all** (27 projects are creatable; VPMGOV is not). A creatable project `NF — N8N Flows` exists but has different issue types (`New Workflow Request`), so which project the audit deploy tickets belong in is an OPEN DECISION, not something to settle by picking whichever the API allows.

- 2026-08-30 — **`check_id` is a Security Room portal id, not a build-time field; the pipeline never mints one.** Asked to assign a `check_id` to the two staged flows that lack one. Did not. The queue answers the question itself: the **Wellcare Advanced Clinic** row carries, in the `check_id` field, *"n/a — this check has no Security Room delivery (workbook + email draft + runs log only). Assign one only if it is ever pointed at the portal"*, and **CC Overstay Fines** sits at Staging with `check_id` null. So a null is normal and a minted UUID would be an id the portal cannot resolve — a silent linkage break, in a field whose whole purpose is external linkage. Compounding it: the flows stamp their OWN `check_id` into their Runs data tables as a slug (`applicant-real-ticket`, `mv-monthly-payment`, `manual-cc-price-by-cohort`), a different namespace from the Notion field's UUID (`7d6e0c41-…` on Dummy Tickets, which appears nowhere in any flow) — so "copy it from the flow" is wrong too. Assertion 8 of the readiness gate ("check_id assigned") is **withdrawn**; it was gating on a field that is legitimately empty for most checks. Written into SKILL.md Phase 8, the design doc's status protocol, and the readiness report §2e.

- 2026-08-30 — **Status transitions are pipeline-owned at fixed moments; the Jira stage is not.** Standing rule from Hassan. `Tech Owner` = Hassan is set when a build STARTS (Phase 5, before the first node), not when it finishes — the 2026-08-30 readiness run found three built-and-running flows still reading *Spec'd — pending build*, which is exactly what an unowned in-flight build looks like. `Status` → `Built on n8n — Staging` is written by the build the moment the flow lands in staging (new Phase 8), together with `n8n Staging Link`, `Flow Version` and `check_id`; it asserts where the CODE is, not that it is correct, so Phases 6–7 and the results-validation gate are untouched. `Status` → `On Jira pending production` is NEVER inferred — that stage asserts a human raised the deployment ticket, so the operator reports it and supplies the URL. Same posture as *draft, do not post*. `/audit-queue` stays strictly read-only: the gate reports, the build writes. Written into `.claude/skills/erp-audit-flow-builder/SKILL.md` (Phases 5 + 8, and a fourth entry under "Where humans are required") and `design/spec-to-jira-pipeline.md`.

- 2026-08-27 — **ERP route ban audited for the first time; every flow held on disk breaks it.** The 2026-08-25 Dead-End Routes doc bans thirteen paginated routes from specs AND n8n flows, and no sweep had been run. MV Stage 2 called `/accounting/payments/page/advancesearch` (the endpoint the doc records as having taken Accounting ERP down once), MV Stage 1/0 call `/clientmgmt/contract/search/page`, and Applicant, Dummy Tickets and Terminated HM all call `/accounting/transactions/page/advancesearchNew` — Section A, no alternative, an ERP-team ask. Record: `records/route-swaps.md`.
- 2026-08-27 — **MV Stage 2 ledger swapped to `POST /accounting/payments/search` via a name-inheriting adapter, not a URL edit.** The scorer reads the ledger by node NAME and its completeness guard reads a page envelope (`content` / `totalElements`), which a bare list does not have — a URL-only swap would have sent every contract to gate `surface` and produced a run of nothing but pendings. Editing that guard means rewriting ~700 lines of parity-guarded core, refused for the same reason as D5/D6. Instead the HTTP node was renamed and an adapter took the old name, after **testing on a throwaway workflow** that n8n's `renameNode` rewrites connections but not `$()` inside Code bodies. Core verified byte-identical afterwards. The adapter passes non-200 through RAW so the circuit breaker can still see `<LOGOUT>`, and handles the envelope shape too because the ban doc warns a path without `page` can still page. 10/10 unit tests.
- 2026-08-27 — **MV Stage 1/0 contract-search swap NOT attempted, deliberately.** It is a rebuild, not a swap: Stage 1 uses the banned route as a *counter* (`size=1`, read `totalElements`) and no replacement is a count endpoint; Stage 0 is a two-pass head/tail pager built around that endpoint's page-0 40-row cap, which the cursor replacement makes obsolete rather than adjustable; and the replacement's response shape cannot be verified because `.env` is absent so `ask-code.sh` cannot run. Rebuilding a population sweep blind against the module that has already been taken down once, on a flow whose own note says UNTESTED, is not a call to make unilaterally. Unblocked by restoring `.env` plus a decision on how the run is counted and costed.
- 2026-08-27 — **The `superseded` backfill was applied by RULE, not by setting everything false.** The 24 rows predating the column held NULL, so `superseded = false` returned nothing. Setting them all `false` would have been a lie: MV ids 3–4 and CC id 4 genuinely are superseded. The rule applied instead ranks **runs** (not rows) by `createdAt` within each group and retires all but the latest — 14 → true, 10 → false, verified from a fresh read. Ranking by row would have marked three of `mvmp-2026-07-full`'s own four slices superseded by the fourth. Approved by Hassan after a dry run. Records: `records/backfill-plan.md`, `records/backfill-applied.md`.
- 2026-08-27 — **Supersession stamps exclude their own `run_id`; `neq` IS supported on a string column.** The stamps shipped matching `check_id + window_from` only, on the reasoning that at stamp time every match is a predecessor by construction. That is false for MV, which writes **one Runs row per slice**: slice 2 would have superseded slice 1 until only the last slice survived, under-reporting a whole month — worse than the double-count D16 fixed. The node note had recorded `neq` as untestable; the dry-run harness tested it and it works. Added to all five stamps: load-bearing on MV, a deliberate no-op on the other four so the pattern stops resting on an unenforced per-flow fact. Record: `records/dry-run-result.md`.
- 2026-08-27 — **D5 and D6 shipped as a separate wrapper node, not an in-place wrapper edit.** `jsCode` is one parameter, so a three-line wrapper change means rewriting ~700 lines of parity-guarded core; a transcription slip there is exactly what `test-node-parity.js` exists to catch, and relying on that test to catch our own typo is the wrong order. Both rules are presentation rather than scoring, so `Apply Scope & Gap Rules` between the scorer and the writer is the honest home. Parity holds by construction — the core was never written to. Parity confirmed passing by Hassan. Record: `records/d5-d6-pushed.md`.
- 2026-08-27 — **D6 corrected from its own draft: the signed gap is suppressed on a contract's first month.** The patch-kit draft applied the difference whenever both figures were known. The core suppresses the amount comparison on a start month (`amountTestable = isNum(expected) && !isStartMonth`) because a partial first month can legitimately receive less than a full instalment and still be CLEAN — so the draft would have printed positive gaps on clean rows, re-manufacturing the false-red shape D14 and D2 remove. Cost: the wrapper now duplicates one line of core logic (`isStartMonth`), noted in the node so it tracks any core change.
- 2026-08-27 — **D5 is scoped to gates 1 and 2 only, never to `verdict === 'inconclusive'`.** Gate `surface` (ERP unreadable), gate 5 (`is_pre_collected` unreadable) and gate 4's no-rows-no-expectation are also inconclusive and BELONG in the reviewer queue — they are things the check could not READ, not things it declined to JUDGE. Widening the test would hide real read failures behind a scope label, which is the worse error.
