What this check does

Section one of two · for the owner

What a finding means

The company bought a real flight for a recruitment applicant. She did not travel on it, and the money was never refunded. That is money out for something that never happened — so the case opens a recovery question. It does not authorise any payment, and nothing moves as a result of it.

A second ticket is not a finding. Multiple real tickets on one applicant is normal and expected: visa timing slips, applicants miss flights, airlines get switched, and a domestic feeder leg is booked separately from the international one.

Of the applicants a naive “two or more tickets” count flags in a complete month, none are duplicate-booking losses. The business already handles duplicates correctly — it refunds the unused ticket. What it does not always recover is a ticket that simply went unused. That is the gap this check looks for, and it is why the count is only a trigger, never the finding.

What the check deliberately does not cover

Each of these is out of scope by decision, not by omission.

Not coveredWhy
Dummy ticketsA separate check owns those. The two share applicants, so only the ticket’s own type separates them.
Housemaid tickets in the same expense bucket37 of 387 rows in July. Excluded here — and currently owned by no specced check. Raised as a gap.
Whether a fare was expensiveNot this check’s question. Only whether money spent produced a flight or came back.
Booking hygieneA dummy ticket mis-filed into the real bucket is a data-quality issue for Accounting, not a loss.
Currency conversionEvery money-bearing row measured was already in AED. A foreign currency routes to a person rather than being converted.

Two of those numbers will move if you re-run the check, and two will not. Money out is arithmetic — it came back identical across two runs of the same month, along with all 23 other counted figures. Explained and unrecovered depend on an AI reading the written record, and it does not answer identically every time.

Measured on two runs of July: money out unchanged at 24,016.99, but unrecovered moved from 16,185.60 to 18,319.45 — a swing of 2,133.85, because the model explained one loss on the first run and declined to on the second. Do not quote “unrecovered” as a hard total without someone reading the 20 judgements behind it. They are all listed, with the exact sentence each one rests on.

What each band refuses to do

The guards are the reason to trust the numbers, so they are worth reading as carefully as the steps.

BandDoesRefuses to
01 IntakeTakes the ERP token per run; nothing is stored in the flow.Report an expired token as a server fault, or audit a month that has not finished.
02 PopulationWalks 40 rows a page and proves the count matches ERP’s own total.Trust an absence before that proof passes. Ask for a bigger page — ERP silently caps at 40 and the skipped rows look like they do not exist.
03 IdentityReads the applicant id; nets a refund against the charge it reverses.Match anyone by name. Count a refund as a second ticket.
04 Ticket readsReads every examined applicant’s ticket record.Skip an applicant because her ticket count looks unremarkable — a single lost ticket is a full loss.
05 GatesScores each ticket, first match wins; the case takes the worst.Let a later clean overwrite an earlier routing decision. Treat a money-less booking shell as a ticket.

07 Verify · storeAsks the AI only about the residue; writes 262 case rows.Let one explained loss close another. Delete an explained amount from the total. Record “unsure” as clean.

How much of this is the AI?

Very little, and it is separable — which is the point.

Decided byCasesWhat decided it
deterministic246Arithmetic and recorded fields only. Reproduces identically every run.
AI examined16Of these it explained 6 and refused to clear 10. It can only ever clear a loss with a verbatim quote from the record.

The AI never scores a ticket, never computes an amount, and never decides whether a refund exists — all of that is settled before it is asked anything. Its only question is “does the written record state a decision that accounts for this money?”, and every answer it gives is stored with the exact sentence it relied on, so each one can be checked in about ten seconds.

Declared gaps

Read before quoting any figure

This flow is a draft and has never been published or scheduled. It runs only when someone triggers it by hand. Nothing reaches the Security Room portal — no callback path has been issued for this check, so that delivery is deliberately inert.

A rule the spec left undefined is now live

Jacky

“Same route booked twice, nothing recovered, no reason given” was left without a red because the spec found zero instances. Across the full population there is one. The shape is no longer hypothetical, so the deferred ruling is needed: may it conclude a finding, or keep routing to a person?

The zero-value floor still needs confirming for this check

Jacky

Applied as zero on the measurement that any higher floor would hide real losses — confirmed reasoning for the sibling check, not yet explicitly for this one.

37 housemaid ticket rows are owned by no check

Malaz

Excluded here as out of scope, and the check once assumed to own them has been confirmed as a different expense entirely. Nobody is currently looking at them.

Two specs cover this same ground

Malaz

A separate “Duplicate Applicant Ticket Audit” spec targets the same population with a conflicting rule that would escalate every multi-leg journey. Only one should be built.

Findings are attributed to the wrong person

operator

Every run so far was read under a colleague’s ERP token, so ERP’s audit log and the run record both name Abdullaha. Re-running under the operator’s own token fixes the attribution and also proves that account holds all five permissions this check needs.

One joint in the logic is a heuristic

noted

Linking a ticket to the transaction that paid for it has no defined method — the reference code exists only in the payment’s description, not on the ticket, so amount matching is the only join available. It fails on 4 of 262 applicants, each of which routes to a person rather than being cleared.

Two recorded ERP behaviours were not re-verified in this build

noted

That a “contains” search still errors, and the 40-row page cap. The flow is built the safe way round in both cases.

One of the spec’s five test cases can never pass again

noted

Its expected answer depended on a flight being in the future. The applicant has since flown it, so the case now correctly comes out clean. It needs a frozen date or a replacement.

Eight corrections have been filed back to the check’s spec page as a marked build-feedback section, including the one that matters most for reading any earlier number: the spec’s headline figure of AED 7,048.55 was measured on 40 of 262 applicants and is a sample, not the month.
