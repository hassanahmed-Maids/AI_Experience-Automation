## What failed

### 1. Chunk 2 never launched — self-continuation needs an ACTIVE workflow

```
Launch Next Chunk: "Workflow is not active and cannot be executed."
```

Fire-and-forget `Execute Workflow` (`waitForSubWorkflow: false`) queues an
independent **production** execution, which n8n refuses for an unpublished
workflow. Stage 1 → Stage 2 worked only because Stage 1 ran manually, so its
child ran in `integrated` mode.

This is a genuine constraint, not a wiring mistake, and it has no in-draft
workaround: setting `waitForSubWorkflow: true` would run chunk 2 integrated and
succeed while draft, but then each chunk's clock nests inside its parent's and
the whole chain shares one 2400 s budget — which is the exact thing chunking
exists to avoid.

So: **the chunk chain only works once Stage 2 is published.** Not doing that —
the standing rule is that these stay drafts, and publishing is Moe's call.

### 2. Stage 1 was dropping the free inline fields — FIXED

`Assemble Baton` read `maidLiveOut` / `startDate` / `clientId`, the *dynamic API*
names. The fallback route uses `liveOut` / `startOfContract` / `client.id`. All
5,393 contracts therefore reached Stage 2 with `live_out` and
`contract_start_date` **null**:

```
live_out_nonnull: 0    start_nonnull: 0    (of 5393)
```

Stage 2 silently recovered both from the per-contract details call, so the run
still scored — which is exactly why this would have gone unnoticed. The real
cost is robustness: any contract whose details call fails loses its living axis
and start date too, when both were available for free from the population pull.

This was identified in the probe write-up and never carried into the code. Fixed
in Stage 1: fallback names first, dynamic-API names retained as fallbacks so the
same node keeps working when that route opens.

**Not yet re-run after the fix** — a re-run means another 15-minute full
population pull, so it is queued rather than done.

# Page-size test, 2026-08-18

## Larger page sizes are a silent-data-loss trap — keep size=40

Requested size vs what comes back, page 0:

| size | rows returned | total | seconds |
|---|---|---|---|
| 40 | 40 | 5394 | 5.4 |
| 100 | **40** | 5394 | 6.3 |
| 200 | **40** | 5394 | 8.4 |
| 500 | **40** | 5394 | 14.5 |
| 1000 | **40** | 5394 | 25.9 |

The row count is clamped to 40 no matter what, but **response time scales with the
requested size** — the server does the larger query and throws most of it away.

The dangerous part is the offset. `page 1, size 200` returns firstId **1006755**,
which is exactly `page 5, size 40` (5 × 40 = 200). So the offset is computed from
the **requested** size while only 40 rows are returned:

```
size=200:  page 0 → rows   0.. 39     rows  40..199  NEVER RETURNED
           page 1 → rows 200..239     rows 240..399  NEVER RETURNED
           ...
```

That is an **80% silent loss** behind a healthy HTTP 200 on every request. The
handover's "larger sizes were not accepted" is right in outcome but badly
understates it — they *are* accepted, they just quietly skip most of the
population.

**Verdict: size stays 40.** Stage 1's ~15 minutes is the real cost of a complete
pull, not an inefficiency to optimise away.

Worth noting the hardened population guard catches this exact failure: at
size=200 the pull yields ~1,080 rows against a reported total of 5,394, which
trips the unconditional SHORT READ abort. The guard is doing real work.

## Ordering is stable — pinned it anyway

The default (`sort` empty) order is already **strictly ascending by id**, and an
explicit `sort=id,asc` is honoured and returns identical rows; page 1 continues
exactly where page 0 ends.

This is what makes a 15-minute paged pull safe against concurrent inserts: new
contracts take high ids and append **past** the read cursor, so rows already
fetched never shift and nothing is skipped. Stage 1 now pins `sort=id,asc` so
that guarantee is contractual rather than an undocumented accident.

## Population drift

`total` observed across the morning: **5392 → 5393 → 5394**, roughly one per
hour. Small enough that the guard's 1% divergence band is unaffected (one row is
0.02%), and harmless given ascending-id ordering. Recorded because the check's
own numbers will move between runs, and a reader comparing two runs should know
the population itself is live.

# CORRECTION: no case was ever written. The Cases table was empty.

Going to clear the "40 smoke rows" found there were none. `Read All Cases`
returned zero rows. Both earlier smoke runs reported cases written; **none were**.
The claim in the sections above that 10 and then 30 rows "landed in the Cases
table" was wrong — it was read off the node reporting success, not off the table.

## Root cause

```
Validation error with data table request: unknown column name 'nationality_source'
```

`Score Batch` emits `nationality_source` for provenance. It was never a column on
the Cases table, so the data table rejected **every** row.

Isolated with three inserts side by side:

| insert | result |
|---|---|
| `defineBelow`, explicit schema | inserted (id 1) |
| `autoMapInputData`, only real columns | inserted (id 2) |
| `autoMapInputData`, one extra non-column field | **rejected** |

So the mapping mode was never the problem. One unknown field kills the whole row.

## Why it was invisible — three layers of silence

1. **`onError: continueRegularOutput`** on Write Cases swallowed the validation
   error and let the loop continue.
2. **`optimizeBulk: true`** suppresses returned data, so the node's output was the
   passthrough input — which *looks* exactly like a successful insert.
3. The loop's next node was a Wait, so nothing downstream ever touched the result.

The run therefore scored contracts, reported `cases_written_to`, advanced its
cumulative counter, and persisted nothing. This is precisely the failure mode the
whole check is built to avoid, reproduced inside the check's own plumbing.

## Fixes

- `nationality_source` added as a real column, so provenance is kept rather than
  dropped — it matters most while the source is `unavailable`.
- Write Cases is now **`onError: stopWorkflow`** with 3 retries and a 1 s backoff.
  A rejected insert kills the chunk loudly; a transient blip retries. Cases
  already written persist, so a rerun resumes rather than repeats.
- Verified by inserting the exact field set Score Batch emits: it landed with
  every column populated, `nationality_source: "unavailable"` included.
- Stage 2 re-published so the fix is live. Probe rows deleted; table is empty.

## The lesson worth keeping

`optimizeBulk` plus `continueRegularOutput` on a write node is a silent-data-loss
combination. Never trust a write node's own output as evidence the write
happened — **read the table back**. Applies to every data-table write in this
system, not just this one.
