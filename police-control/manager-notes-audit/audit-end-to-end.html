Police & Control · Manager Notes Audit

End to end: a note arrives, a verdict comes out

Every month managers add money to housemaid payslips. Each addition is supposed to be justified by the rule governing that payment type, and nothing checks it. This is the whole path a single addition takes — what runs today, what is blocked and on whom.

The path

Stages in order. The two red items are the ones that produce a confident wrong answer rather than an error — they are the reason this reads as a pipeline and not a checklist.

01

Population

runs today

44,169 addition notes exist. Scope is one row per manager note — a maid with four additions is four cases.

  • ADDITION on a housemaid, applied, not a refund
  • 🔴 PAID = true is NOT a scope filter — it means “carried-forward must-be-paid”, and filtering on it drops most of the population and reports the month clean
  • Negative and zero amounts stay in — reported, never netted away
  • Future-dated notes are a feed defect, not an unverifiable case
02

Audit month

runs today

Which payslip actually paid this note. Three branches, because the ERP populates the paid-month columns for only some notes.

  • Recorded → PAID_ON_PAYROLL_MONTH
  • Derived → the payroll lock window containing the note date
  • Neither → in the population, AMBER, never dropped
  • 🔴 NOTE_DATE carries a time. NOTE_DATE = LAST_DAY(...) is false for every row and returns a plausible, meaningless split
03

Test battery

partly blocked

Seven cross-cutting tests plus one group rule. Every applicable test runs and is recorded — there is no early exit.

  • T1 profile · T2 payment type · T3 amount usable
  • T4 authorising expense record — blocked: no FK exists, and EXPENSES_REQUESTS is not granted
  • T5 expense head · T7 contract-type eligibility — blocked on three reference lists that do not exist
  • T6 duplicate — runnable
  • Group rule — one per payment family, nine reusable mechanisms behind them
04

Two obligations on every test

new in v3

Both learned by getting them wrong on live data.

  • A window test publishes its chance rate: a 105-day window with a 30-day band gives p=0.286, so at 1.7 records per subject chance alone yields 40%
  • A control metric publishes a 24-month series: a point count renders a broken control, a worked-off backlog and a holding control as one number
05

Verdict

runs today

One column, computed once. Every tile, chart, filter and export aggregates it and nothing re-derives eligibility.

  • RED ⟸ any applicable test returned RED
  • AMBER ⟸ not red, and any applicable test was BLOCKED
  • GREEN ⟺ every applicable test ran and returned GREEN
  • 🔴 A test that could not run is not a test that passed — and an unmapped payment type yields an empty check plan, so it arrives AMBER, never a silent green
06

Metrics

runs today

Ten named metrics the auditor reads, aggregating the one verdict column. M7 + M8 + M9 = M1 exactly; amounts sum to M2 to the cent.

  • M1 Cases · M2 Money · M7 Findings · M8 Unverifiable · M9 Cleared
  • M10 Coverage · M11 Amount at Risk · M12 Duplicate groups
  • M13 Expense match rate — per payment type, with an 80% floor per type
  • M14 Completeness exceptions — one row per maid × payroll month
Spec v3, 2026-09-08. The first version corrected by querying live data rather than reading catalog metadata and ERP source alone — eleven queries that changed the logic in eight places and withdrew two claims the earlier versions made confidently. Amber is a result this report publishes, not a failure of it: a test that could not run is never counted as one that passed.
