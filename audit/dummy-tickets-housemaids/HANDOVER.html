What this replaces, and why

The live check flagged everything that was not already refunded. Because gates 50, 90 and 100 did not exist in it — requestRefundOn was never read at all — five of the seven ticket statuses that occur in production were published as red flags against named applicants. A refund that simply was not due yet, a cancelled shell carrying no money, and an ERP outage were all indistinguishable from a loss.

The completeness landmine is live on this endpoint

The page envelope carries both keys: total: "" — an empty string — and totalElements: 137, a number. This is the exact shape that truncated the sibling CC sweep at 24,000 of 29,772 rows and published thousands of false reds on a run that reported success.

The rebuild asserts on totalElements and aborts on any non-numeric declared total. The flow it replaces asserts nothing here at all, so it is not bitten today — but any future change that reads total would truncate silently.

What differs from the golden

Procedural deviation — this is not a literal clone

The build procedure says to clone the golden and not re-generate the webhook and validation nodes, pagination, carry-forward handling, the callback nodes, the error rail, verdict merging, or the AI agent's wiring — and to stop and say so rather than improvise a skeleton change.

Validate Inputs is the golden's, verbatim, including the shared secret, the callback-URL allowlist and the bearer shape check. Everything else in that list was re-implemented rather than cloned, because the data budget forced a shape the golden does not have: ~1,200 transactions and 605 applicants per month cannot be enriched inside one execution, so enrichment moved into a chunked sub-workflow returning slim projections.

This carries exactly the regression risk the cloning rule exists to prevent. Two of the bugs found during this build were in re-implemented skeleton territory. Worth an explicit decision: either accept the divergence and treat these two flows as a second skeleton, or fold the chunked-enrichment shape back into the shared golden so every check gets it.

Pacing

Every per-record ERP call runs at the house limit — 5 concurrent, 500 ms between batches — and chunks run sequentially. The flow this replaces ran its detail sweep at 10 concurrent / 200 ms. Across the June run that meant roughly 1,200 authenticated reads with zero ERP failures, which matters given the shared account has already been disabled once by an unpaced burst.

Verifier

Both verifier rules are built. Enforcement lives in Merge Verdicts, not the prompt: only EXPLAINED or CLAIMED_OFF_ERP with a quoted sentence may move a ticket, a claimed off-ERP refund downgrades to pending and keeps the amount as a claim rather than writing it off, and everything else leaves the gates' verdict standing. There is no path by which a confirmed loss becomes clean.

On the June run all 7 findings were adjudicated, every one had a written record, every one returned NO_CLAIM, and every finding stood.

Declared gaps

Each travels with every run in record.declared_gaps. A quietly absorbed gap is worse than a loud one.

Verifier rule 1 has never been exercised on live data

No dummy ticket with outcome Used has appeared in any window run — not in 93 applicants, not in 605. The flown-on path is covered offline only. Do not record it as validated.

Gate 100's date-based half has never fired

It fires only through the blank-schedule ruling. No ticket past a real requestRefundOn plus 30 days has been observed in any run, consistent with the spec's own measurement that the auto-refund scheduler is 100% on time. Keep the gate as the guard for the day that stops being true; do not mark that half validated. DoNotRequestRefund has also never been observed on a DUMMY ticket.

Charges that cannot become cases

June produced 15 charges carrying no applicant id in the description and none on the transaction detail. They cannot be applicant-scoped cases — one case is one applicant — so they are listed in the workbook as needs_attribution with their transaction ids, and are not adjudicated and not counted in any verdict total. They need manual attribution. May produced none, which is why this only surfaced at month scale.

The workbook is a deviation from the spec

The spec's Where do the results go? has portal and runs log ticked and Workbook unticked, and this check is marked Handles sensitive data = YES. The workbook was added on request.

Mitigated by writing identifiers and amounts only. Deliberately excluded from every tab: applicant names, passport numbers, and card-holder or staff names. Passport numbers are also stripped before anything reaches the model. A Sheet is far easier to forward than a portal case, so who the file is shared with is a live decision.

What still needs a human

1 · Re-verify on the operator's own ERP identity

Every measurement in this document was taken on a bearer token whose user claim is not the operator's, at the owner's explicit instruction. ERP logs every read under the token's identity, so findings would attribute to someone who did not produce them — and where that person also reviews the cases, it makes the reviewer the actor in their own evidence.

Nothing here should be marked Technical Validated until it is re-run under the identity that will own the findings. Set the n8n workflow variable ERP_BEARER; the flow holds no ERP credential of its own and fails with a clear message rather than silently borrowing one.

2 · Repoint the portal — done 2026-08-19

Repointed from the n8n side rather than the portal side. The check's registry row lives in the Security Room's Supabase project, which was not reachable, so this flow adopted the retired flow's webhook path instead: the URL the portal already stores, /webhook/applicant-dummy-ticket-refund-audit, now resolves here. /webhook/dummy-tickets-housemaids no longer exists.

No portal-side payload change was needed. This flow's validator is the golden's, and the golden is what the portal already drives: the same shared-secret header, the same callback-origin allowlist (it is literally the portal's two callback hosts), a 31-day span cap that fits the portal's previous-calendar-month default, and backwards-compatible reading of the legacy auth.erp.token field the old flow used.

Verified by POSTing the production path with no secret: it answered {"accepted":false,"message":"unauthorized"} — the new validator's terse security rejection. The old flow had no secret check and would have replied with a missing-field error. That flow is now archived, which both prevents a republish from taking the path back and closes its unauthenticated-webhook exposure for good.

The trigger stays manual. The cutover added a route, not automation. The flow has exactly two entry points and both are human-initiated: the portal webhook, which fires only when someone triggers the check in the portal, and Run Manually in n8n. There is no Schedule or Cron node anywhere in either flow, and none will be added here — a standing unattended run is an ERP/Data team decision, not a build one.

Watch the first portal-driven run. If the portal does not send the shared-secret header for this check, every call is rejected — and that branch is deliberately silent, so that anyone who finds the URL cannot mail-bomb the team. The portal would look like it ran and produce nothing. Confirm in the n8n execution list rather than assuming.

3 · Sign-off before findings reach reviewers

Test cases verified, Business Validated and Technical Validated are still unticked on the spec. The spec's own answer to independent review is no — on the grounds that the Security Room reviewer working each case is the second pair of eyes — so that reviewer is the control, and it only holds once cases actually reach them — which, now that the portal is repointed, depends only on sign-off.

Also open, and lower stakes: the repeat-booking threshold deserves a second look against the month-scale number, and the skeleton divergence above needs a decision about whether the chunked-enrichment shape folds back into the shared golden.
