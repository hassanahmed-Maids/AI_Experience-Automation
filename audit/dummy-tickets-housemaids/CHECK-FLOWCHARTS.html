What this check does

Section one of two · for the owner

What a finding means

A dummy ticket is a real, paid flight booked so an applicant has something to show a visa office — reassurance on paper, never intended to be flown. It is always supposed to be refunded. A finding is a dummy ticket the company paid for where the refund never happened. The case opens a recovery question worth the ticket's own cost; it authorises nothing and moves no money by itself.

“Not refunded yet” is not a finding. Most dummy tickets carry a scheduled refund date, and the scheduler is reliable: across everything measured it has a 100% on-time record. A ticket whose refund is simply not due yet is pending, not a loss.

This is the single biggest change from the check that ran before. That one flagged everything not already refunded, so a refund three weeks from due, a cancelled booking shell carrying no money, and an ERP outage all looked identical to a real loss. On the same window it published ~32 red flags where this one publishes 4.

What the check deliberately does not cover

Each of these is out of scope by decision, not by omission.

Not coveredWhy
Real applicant ticketsA separate check owns those. Both read the same ticket list on the same applicants, so the ticket's own type is the only thing keeping them apart.

Whether the ticket should have been boughtThis check asks whether the money came back, not whether the booking was justified.

Parked, never sized—207 cancelled shells carrying no amount. Counted as pending, deliberately absent from the total.

The repeat-booking number is a threshold, not a discovery. The 281 booking reviews are cases whose money verdict is clean — surfaced only because the threshold for “repeated bookings” is currently set to 2. That is 40 reviews for every actual finding.

The same population at other thresholds: 3 → 160 · 4 → 81 · 5 → 44 · 6 → 18 · 8 → 5. No money figure changes at any threshold — findings stay at 7 and unrecovered at 22,611.54. It is purely review load, and it is one setting. The threshold was chosen against a 5-day window; this is the first month-scale number available.

The judgement layer was stable across two runs — unusually, for an AI reading free text. June was run twice: both times all 7 findings were adjudicated, all 7 came back no claim of a refund on record, and all 7 stood. Money out was identical to the cent.

That is two observations, not a guarantee. What is guaranteed is structural: the model cannot clear a loss. Only a quoted sentence can move a ticket, and the strongest thing an accepted claim can do is park a finding as pending with its amount intact — never write it off.

How it works

Section two of two · technical

What each band refuses to do

The guards are the reason to trust the numbers, so they are worth reading as carefully as the steps.

BandDoesRefuses to
01 Intake Takes the ERP token per run; the flow stores none of its own. Checks a shared secret and an allowlist of where results may be sent. Report an expired token as a server fault — ERP returns a 500 for it, not a 401. Send results anywhere the caller names.
02 Population Walks the dummy-ticket expense for the window and proves the rows pulled equal the total ERP declares. Trust an absence before that proof passes. Read the endpoint's other total field — it returns an empty string, which silently becomes zero and certifies a flawless walk of a truncated set.
03 Identity Reads the applicant id from the charge description, with a per-charge lookup as fallback. Match anyone by name — two applicants sharing one would merge into a single case and hide one of them.
04 Ticket reads Reads every examined applicant's ticket record, 25 applicants per sub-flow execution. Let an applicant vanish silently. Every applicant asked for must come back or be recorded unreachable — this caught 68 of 93 going missing on a run that still reported success.
05 Gates Scores each ticket, first match wins; the case then takes the worst of its tickets. Filter the population on the ticket's task label — it flips the moment a refund is raised, so filtering on it drops the refunded tickets this check exists to inspect. Treat a money-less shell as a sized loss.
06 Refund hunt Searches the applicant's whole charge history with no date filter, for findings only. Conclude “never refunded” from a call that was not proven complete. Use the wrong search operator — one returns a 500 and once led to the whole route being written off as permission-blocked.
07 Verify · store Has the model read the written record; writes the durable run record before any display target. Let the model clear a loss. Only a quoted sentence moves a ticket, and an accepted off-system refund claim parks the finding as pending with its amount intact — it is never written off.

Two failures found during the build were the same species, and both are the reason the guards above are worded as refusals rather than steps.

The enrichment step silently returned only the first chunk, so 68 of 93 applicants were never scored — and the run reported success with a plausible-looking record. Separately, the ticket notes were being stripped before the model saw them, so it answered no written record on every finding; four unanimous such answers look exactly like a population that genuinely has no notes. Both were caught by assertions on the input, not by any error.
