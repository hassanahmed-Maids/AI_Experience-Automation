## Description

> ⚠ **Jira is the source of truth for the description.** It has been edited twice since filing
> (attachments referenced, check-name table added, mockup link raised). The copy below is the
> original and is retained for history — read the ticket, not this section.

### What we need

Police & Control runs ten critical checks on the housemaid payroll every month. They currently run
in a retired automation that is being decommissioned; they are moving to a MaidsInsights dashboard.

That process never queried anything. **A person downloaded two files the ERP already generates and
archives every month, and uploaded them to a portal.** All ten checks are arithmetic on those two
files. So the ask is narrow:

> **Get the contents of these two monthly files into Snowflake.** The logic that runs on them is
> already written up on our side — you do not need to reverse-engineer it.

### The two files

Both are produced by the payroll run and archived per payroll month. The ERP surfaces them at
`/payroll/v2/payroll-archived-files` (`POST /payroll/accountantTodo/fetchPayrollFile`,
`PayrollAccountantTodoController`), which pulls attachments off completed `PayrollAccountantTodo`
rows.

| | Ansari / WPS transfer file | Detailed payroll file |
| --- | --- | --- |
| Attachment tag | `WPSTransferFile` | `HousemaidDetailedPayrollFile` |
| Generated by | `TransferFilesService.generateWPSTransferFile()` | `AuditFilesService.generateHousemaidFinalDetailedPayrollFileNew` |
| Shape | 19 fixed columns; one EDR row per maid + one SCR summary row | 39 columns, one row per maid |
| Grain | one row per maid per payroll month | one row per maid per payroll month |

File bytes sit in object storage; the pointer rows are in `ATTACHMENTS`
(`OWNER_TYPE = 'PayrollAccountantTodo'`, `OWNER_ID` → the todo, `TAG` selecting which file).

### Two ways to do it — your call

**Option A — ingest the archived files' contents.** Exactly what the checks were built and validated
against, so no reconstruction risk. Downside: a file is not a queryable model, so joins and
month-over-month trending have to be built on top.

**Option B — reconstruct from the underlying tables.** Almost everything in both files comes from
`HOUSEMAIDPAYROLLLOGS` and `HOUSEMAIDPAYROLLBEANS`, and `HOUSEMAIDPAYROLLLOGS` is *already* the
source of `HOUSEMAID_PAYROLL_HISTORY`. Likely cheaper, gives history back to 2020-07, and produces
something joinable. Risk is drift — a reconstruction can disagree with the file actually sent.

If it helps: **B for the checks, plus file metadata for assurance** (below). We are not prescribing
either — you know the models and lineage better than we can from outside.

**If you pick B**, most of the missing fields are columns on `HOUSEMAIDPAYROLLLOGS` that the current
model does not project (`TOTAL_PRO_RATED_SALARY`, `MOHRE_PRO_RATED_SALARY`,
`TOTAL_LIVE_OUT_PRO_RATED_SALARY`, `MOHRE_LIVE_OUT_PRO_RATED_SALARY`, `VACATION_SALARY`,
`GROUP_ONE_DAYS`…`GROUP_SIX_DAYS`, `SALARY_TYPE`, `PAY_START_DATE`, `PAY_END_DATE`,
`UNPAID_DEDUCTION*`) — a projection rather than a new pipeline. The tables not in Snowflake at all
are `HOUSEMAIDPAYROLLBEANS`, `MONTHLYPAYMENTRULES`, `REPAYMENTS`, `UNPAIDDEDUCTIONS`,
`UNPAIDDEDUCTIONREPAYMENTS`, `ATTACHMENTS`, `MONTHLYPAYROLLDOCUMENTS`. Full column-by-column mapping,
including the naming traps we hit, is in the attached source-tables doc.

### One extra, cheap: file assurance (metadata only, no file bodies)

Ingest `ATTACHMENTS` (filtered to the payroll owner types and tags) and `MONTHLYPAYROLLDOCUMENTS`,
so the dashboard can show, per payroll month, that each expected file exists, when it was created,
and — via `MONTHLYPAYROLLDOCUMENTS.FILE_HASH` — whether it changed after the month was audited.

Every other check reconciles ERP figures against each other. This one asks whether the artefact that
actually reached the exchange house still matches the payroll the ERP holds. **A file regenerated
for a closed month is invisible to everything else.**

### Four questions we cannot answer without warehouse access

1. **How often is `PAY_START_DATE` non-null?** Check 8 `Ansari Pay Start Date Check` tests that it equals the 1st of
   the payroll month. The file falls back to the 1st when the column is null — so if it is nearly
   always null, that check has been passing on a value the file itself generated. A single
   `GROUP BY` settles whether it is a real control.
2. **The `ANSARI_PAYMENT_METHOD` CASE expression** from the
   `SILVER.HOUSEMAID_MANAGEMENT.HOUSEMAID_PAYROLL_HISTORY` dbt model — `BA_VIEWS` is only a
   passthrough and that schema is not readable to us. The ERP classifier has **seven** outcomes where
   the model's profiled values show five. If the model drops the `PAYROLL_CARD` and
   `OVER_THE_COUNTER` branches, those accounts fall into `''` and check 9
   `IBAN Red-Flag Transitions vs Previous Month` cannot see them.
3. **Polarity of `IS_DELETED` / `EXCLUDED_FROM_PAYROLL`** (`VARCHAR '00'/'01'`). Guessing wrong
   empties the population.
4. **`CLIENT_MANAGEMENT_PAYMENTS` admits six payment types and not `TYPE_OF_PAYMENT_ID = 1`**, the
   recurring monthly client payment. That omission alone blocks two of the ten checks — is it
   intentional?

Warehouse compute to answer these ourselves is **DNA-9437** (no new object access requested there).

### On sensitivity — so it does not stall at intake

These files contain per-maid salaries and bank account numbers. **This is not new exposure to
Snowflake:** `HOUSEMAID_PAYROLL_HISTORY` already holds the same fields for ~1.3M rows under
role-based access. What made the predecessor unsafe was an *ungoverned* store — retained run
histories holding 25,290 unredacted rows alongside live ERP session tokens, with no access
boundary. A governed warehouse table under existing RBAC is a different thing, and this ticket
retires the ungoverned copy.

**The dashboard built on top does not mask, and that is deliberate.** Its audience is a Police &
Control auditor working payroll findings — an allegation that a specific worker's pay reached a
specific account cannot be investigated against `Maid #4471` and `••••9902`. So the control sits on
**access rather than display**: a dedicated Snowflake role granted to named P&C auditors only,
access and exports logged and readable, no emailed report body (link only), and no export path
wider than the screen. Fields no check reads — phone, EID, passport, client contact details — are
never selected at all.

We would rather have this on the record than discover it at review: if Compliance wants sign-off on
the role membership before go-live, say so and we will build that gate in. Please raise it with us
rather than cancelling the ticket.
