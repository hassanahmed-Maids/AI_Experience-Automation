# Where the payroll-checks data comes from in the ERP

For the DNA / Data Engineering team. Everything below was confirmed against the ERP codebase via
the Low-Code Platform ("Ask the Code") on 2026-09-02/03 — none of it is guessed.

**The short version.** The ten payroll checks have always run on **two files the ERP already
generates and archives every month**. The retired n8n flow did not query anything — a person
downloaded those two files and uploaded them to a portal. So the cleanest handover is:

> Get us these two files' contents, however you think best. The logic that runs on them is in
> `SPEC_housemaid_payroll_critical_checks_v2.md`.

We are not prescribing Snowflake objects. Where we happen to know one exists we say so as a
convenience — the mapping is yours, and you know the models and lineage better than we can from
outside.

---

## 1. The two files

Both are produced by the payroll run and retrievable from
**`/payroll/v2/payroll-archived-files`** → `POST /payroll/accountantTodo/fetchPayrollFile`
(`PayrollAccountantTodoController`), which pulls attachments off completed `PayrollAccountantTodo`
rows and emails them.

| | The Ansari / WPS transfer file | The detailed payroll file |
| --- | --- | --- |
| n8n called it | `ansari_data` | `payroll_data` |
| Attachment tag | `WPSTransferFile` | `HousemaidDetailedPayrollFile` |
| Generated by | `TransferFilesService.generateWPSTransferFile()` | `AuditFilesService.generateHousemaidFinalDetailedPayrollFileNew` → `PayrollGenerationLibrary.generateHousemaidPayrollFile` |
| Shape | 19 fixed columns; one EDR row per maid plus one SCR summary row | 39 columns, one row per maid. Headers from `Housemaid Payroll Template.xlsx` row 1, mapped by `HOUSEMAIDS_PAYROLL_FILE_COLUMNS_MAPPING` → `HousemaidPayrollBean` getters |
| Grain | one row per maid per payroll month | one row per maid per payroll month |

A third file, the **Ansari payment work order (PWO)**, is stored separately on
`MONTHLYPAYROLLDOCUMENTS` (`TYPE = 'PPWO'`, keyed by `PAYROLL_DATE`) and carries a **`FILE_HASH`**
MD5 checksum. It is not an input to the checks, but it enables a control — see §5.

Storage: file bytes go to object storage via `Storage.storeTemporary`; the pointer rows live in
**`ATTACHMENTS`** (`OWNER_TYPE = 'PayrollAccountantTodo'`, `OWNER_ID` → the todo, `TAG` selecting
which file, plus `NAME`, `SIZE`, `EXTENSION`, `PATH`, `AMAZON`, `_SOURCE`).

## 2. Two ways to give us the data — your call

**Option A — ingest the archived files' contents.** Exactly what the checks were built and
validated against, so there is no reconstruction risk. The downside: a file is not a queryable
model, so joining, trending and month-over-month comparison all have to be built on top.

**Option B — reconstruct from the underlying tables.** Almost everything in both files comes from
`HOUSEMAIDPAYROLLLOGS` and `HOUSEMAIDPAYROLLBEANS`, and `HOUSEMAIDPAYROLLLOGS` is *already* the
source of `HOUSEMAID_PAYROLL_HISTORY`. Likely cheaper, gives history back to 2020-07, and produces
something joinable. The risk is drift — a reconstruction can disagree with the file actually sent.

**If it helps: B for the checks, §5 for assurance.** Reconstruct for the monthly numbers, and use
the archived-file metadata to prove the reconstruction still matches what was sent.

**On sensitivity, so it does not become a blocker.** These files contain per-maid salaries and bank
account numbers. That is not new exposure to Snowflake — `HOUSEMAID_PAYROLL_HISTORY` already holds
the same fields for 1.3M rows under role-based access. What made the predecessor unsafe was an
*ungoverned* store: retained n8n executions holding 25,290 unredacted rows alongside live ERP
session tokens, with no access boundary. A governed warehouse table is a different thing. The
dashboard built on top masks names and accounts and never displays an individual salary (§2.4 of
the spec).

## 3. The Ansari / WPS transfer file — 19 columns

Per-employee **EDR** row, in order. Primary source `HousemaidPayrollLog`; `NewRequest` supplies
banking fields when the log's copy is blank; `Housemaid` supplies the name.

| # | Column | Source |
| --- | --- | --- |
| 1 | SN | `HousemaidPayrollLog.sn`, else `"H-"` + sequence |
| 2 | Record Type | `recordType`, default `"EDR"` |
| 3 | Employee Unique ID | `employeeUniqueId`, else `NewRequest.employeeUniqueId` |
| 4 | Employee Name | `employeeName`, else `Housemaid.name` |
| 5 | Agent ID | `agentId`, else `NewRequest.agentId` |
| 6 | Employee Account with Agent | `employeeAccountWithAgent`, else `NewRequest.employeeAccountWithAgent` |
| 7 | **Pay Start Date** | `payStartDate`, **else the 1st of `payrollMonth`** — see the note below |
| 8 | Pay End Date | `payEndDate`, else last day of `payrollMonth` |
| 9 | Days in Period | `daysInPeriod`, else derived from the pay dates |
| 10 | Income Fixed Component | `totalSalary`. **MAID_VISA rows also sum prior-month logs** |
| 11 | Income Variable Component | literal `"0"` |
| 12–19 | Days on Leave, Housing, Conveyance, Medical, Annual Passage, Overtime, Other, Leave Encashment | empty |

**SCR** summary row: Record Type `"SCR"`, **MOL Company Number `"0000000836318"`** (hardcoded),
**Routing Bank Code `"720610101"`** (hardcoded), file creation date and time, Salary Month from the
first included log's `payrollMonth`, EDR Count from `PayrollAccountantTodo.totalIncludedMaids`,
Total Salary as the sum of the EDR fixed components, currency `"AED"`.

> **One question we cannot answer and you may be able to: how often is `PAY_START_DATE` non-null?**
> The file writes it when populated and falls back to the 1st of the payroll month when not. One of
> the ten checks tests that this date equals the 1st. If the column is nearly always null, that
> check has been passing on a value the file itself generated — testing nothing. A single
> `GROUP BY` settles whether it is a real control.

**Three things this settles that were open:**

- **`Earnings of days in grp3` does not exist** — grp3 has a day count only. **grp4 does have
  earnings**, and it is *vacation* salary. So the check that uses grp1/2/5/6 skips nothing by
  accident: grp1/grp5 are full-salary days (live-in / live-out), grp2/grp6 the accommodation
  equivalents, and grp4 is vacation, which does not belong in an accommodation ratio.
  *(This supersedes an earlier, thinner answer of ours that said the enum had no groups 3 and 4.)*
- **`Ansari (AED)` is `Math.round(HousemaidPayrollBean.totalBalance)`**, whereas the Ansari file's
  Income Fixed Component is `HousemaidPayrollLog.totalSalary`. Two different fields that may not
  always agree — worth knowing, since the checks read `Ansari (AED)` while the money moves on the
  other one.
- **`Maid Visa.ae Contract` is not in this file.** It is still populated on the bean (`Yes`/`No`
  from the `maidvisa.ae_prospect` contract prospect type) but was removed from the mapping and now
  appears only in a legacy CSV export. ⚠ **The retired n8n flow used it as its fallback when
  `Type Of maid` came back blank** — so that fallback was reading a column the current file does
  not write. If you reconstruct rather than ingest, prefer `HOUSEMAIDPAYROLLLOGS.SALARY_TYPE`, the
  type snapshotted at payroll time.

## 5. Assurance on the files themselves

Cheap and worth having: **metadata only, no file bodies.** Ingest `ATTACHMENTS` (filtered to the
payroll owner types and tags) and `MONTHLYPAYROLLDOCUMENTS`, so the dashboard can show, per payroll
month, that each expected file exists, when it was created, and — via
`MONTHLYPAYROLLDOCUMENTS.FILE_HASH` — whether it changed after the month was audited.

Every other check reconciles ERP figures against each other. This one asks whether the artefact
that actually reached the exchange house still matches the payroll the ERP holds. **A file
regenerated for a closed month is invisible to everything else in the spec.**

## 6. If you reconstruct — where the fields live

Only relevant under Option B.

| ERP table | Status | Carries |
| --- | --- | --- |
| `HOUSEMAIDPAYROLLLOGS` | **already the source of `HOUSEMAID_PAYROLL_HISTORY`** | Most of both files. Not in the current model: `TOTAL_PRO_RATED_SALARY`, `MOHRE_PRO_RATED_SALARY`, `TOTAL_LIVE_OUT_PRO_RATED_SALARY`, `MOHRE_LIVE_OUT_PRO_RATED_SALARY`, `VACATION_SALARY`, `GROUP_ONE_DAYS`…`GROUP_SIX_DAYS`, `SALARY_TYPE`, `HOUSEMAID_UNPAID_STATUS`, `UNPAID_DEDUCTION`, `UNPAID_DEDUCTION_REPAYMENT`, `PAY_START_DATE`, `PAY_END_DATE`, `DAYS_IN_PERIOD`, `SN`, `RECORD_TYPE`, `AGENT_ID`, `EMPLOYEE_NAME`, `ACCOMMODATION_SALARY`, `PRIMARY_SALARY`, `BASIC_SALARY`, `HOUSEMAID_PAYROLL_BEAN_ID` — **all on the same source table, so a projection rather than a pipeline** |
| `HOUSEMAIDPAYROLLBEANS` | not in Snowflake | `LOAN_REPAYMENT`, `REMAINING_LOAN_BALANCE`, `TOTAL_LOAN_REPAYMENTS`, `TOTAL_LOANS`, `PREVIOUSLY_UNPAID_SALARIES`, `TOTAL_BALANCE` (the `Ansari (AED)` figure), `UNPAID_DEDUCTION*`, `REMAINING_UNPAID_DEDUCTION_BALANCE` ⚠ *a string defaulting to `"N/A"`* |
| `MONTHLYPAYMENTRULES` | not in Snowflake | `PAYROLL_MONTH`, `PAYMENT_DATE`, `LOCK_DATE` (= `PAYMENT_DATE − DAYS_BEFORE_LOCK`), `AUDITING_FINISHED`, `FINISHED`. Several rules per month, each with its own `PAYMENT_DATE` |
| `REPAYMENTS` | not in Snowflake | Per-month loan repayment: `AMOUNT`, `REPAYMENT_DATE`, `PAID_REPAYMENT`, `EXCULDED_FROM_PAYROLL` *(the misspelling is in the schema)*, `EMPLOYEE_LOAN_ID` |
| `UNPAIDDEDUCTIONS`, `UNPAIDDEDUCTIONREPAYMENTS` | not in Snowflake | The unpaid-deduction ledger. No maid-type filter — applies to CC as well as MV |
| `ATTACHMENTS`, `MONTHLYPAYROLLDOCUMENTS` | not in Snowflake | §5 |
| `HOUSEMAIDS`, `EMPLOYEELOANS`, `CONTRACTS`, `WPSRECORDS` | already in Snowflake | maid master, loans, contracts, WPS |
| `PAYMENTS` | partially — `CLIENT_MANAGEMENT_PAYMENTS` | ⚠ admits six payment types and **not** `TYPE_OF_PAYMENT_ID = 1`, the recurring monthly client payment. That omission alone blocks two of the ten checks |

**Traps we hit, so you do not have to.**

- `TOTAL_SALARY` is **net** (what goes to Ansari); `TOTAL_EARNINGS` is **gross**. The Snowflake
  model exposes them under inverted-looking names: `NET_SALARY` ← `TOTAL_SALARY`, and
  `TOTAL_SALARY` ← `TOTAL_EARNINGS`.
- `TOTAL_PRO_RATED_SALARY` is the **full-salary-day** figure; `MOHRE_PRO_RATED_SALARY` the
  **accommodation-day** one. Neither name says so, and swapping them inverts a check into a
  permanent pass.
- Pro-ration divisor is **calendar days in the payroll month**, not 30 and not working days.
  `MAID_VISA` is the exception: 30.4 for group 1, and its `MOHRE_PRO_RATED_SALARY` is 0 by
  construction.
- `STATUS` on the payroll log is **snapshotted at payroll time** — read it there, not from the
  maid's current record.
- `TOTAL_LOAN_REPAYMENTS` and `TOTAL_LOANS` are **lifetime cumulative**. Binding a current-month
  metric to them produced a ratio of ~1,082% that reported as a healthy pass in the predecessor.

## 7. What we would still like from you

1. **A warehouse grant** so we can verify our own claims — filed as **DNA-9437**. Compute only, no
   new object access.
2. **How often `PAY_START_DATE` is non-null** (§3). Decides whether one of the ten checks is real.
3. **The `ANSARI_PAYMENT_METHOD` CASE expression** from the
   `SILVER.HOUSEMAID_MANAGEMENT.HOUSEMAID_PAYROLL_HISTORY` dbt model — `BA_VIEWS` is only a
   passthrough and that schema is not readable to us. The ERP classifier has **seven** outcomes
   where the model's profiled values show five; if the model drops the `PAYROLL_CARD` and
   `OVER_THE_COUNTER` branches, those accounts fall into `''` and the bank-account diversion check
   cannot see them.
4. **Polarity of `IS_DELETED` / `EXCLUDED_FROM_PAYROLL`** (`VARCHAR '00'/'01'`). Guessing wrong
   empties the population.

## 8. Two ERP findings for whoever owns payroll — not data requests

1. **The maid's payment account has no audit trail.** `NEWREQUESTS` is Envers-audited
   (`NEWREQUESTS_REVISIONS`, with `REVISION_TYPE`, per-field `_MODIFIED` flags and
   `HISTORY_REVISIONS` carrying `TIMESTAMP` and `CREATOR`) — but `EMPLOYEE_ACCOUNT_WITH_AGENT` is
   **not in the audited field set**. No approval step, no permission check, no validation: an
   unconstrained `@Column String` that payroll only tests for non-empty. Nobody can say who changed
   a maid's payment account, when, or from what.
2. **Two hardcoded literals** in the WPS summary row: MOL Company Number `"0000000836318"` and
   Routing Bank Code `"720610101"`, both in `TransferFilesService.generateWPSTransferFile()`.
   Neither is a table value or a config constant.
